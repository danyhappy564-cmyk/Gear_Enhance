# 장비 강화 0.6.0 설계

승인한 목업과 능력치 표를 기준으로 구현했습니다. 원본 수리 버프나 아이템 템플릿은 수정하지 않고 아이템·항목별 단계와 계산 후처리로 적용합니다.

## 화면과 조작

`Plugin.View.cs`가 고정 좌표의 전용 IMGUI 창을 그립니다. 승인된 이미지처럼 장비 미리보기·단계, 항목 카드, 현재/성공 후 효과, 비교 막대, 성공률/비용 카드, 실패 안내, 하단 실행 버튼으로 나눴습니다. 게임의 `ItemViewFactory.LoadItemIcon`으로 현재 장비 아이콘을 받고 화면 높이에 맞춰 전체 창을 축소합니다.

보호 체크 칸과 비용 내역을 위한 일반 강화 기본 크기는 760×950, 최대 배율은 1.1입니다. 화면 높이 64px·너비 48px의 여백을 남기는 배율을 택해 중앙에 배치하며 드래그 후에도 화면 경계로 제한합니다. 항목 카드 전체를 클릭할 수 있고 제목과 설명은 같은 영역에 `MiddleCenter`로 고정합니다. 아이콘은 `UiGlyphs`가 48×48 알파 마스크로 한 번만 계산하고 텍스처로 그립니다. 마스크는 CPU에서 생성하고 GUI 행렬 회전은 사용하지 않습니다. 격자도 24×24 텍스처를 반복해서 한 번에 그립니다. 그리기 중 새 GUIStyle·GUIContent 객체를 만들지 않으며, 라벨은 모든 이벤트에서 동일하게 호출해 컨트롤 ID를 유지합니다. 회색 패널·금색 버튼의 작은 그라데이션 텍스처는 최초 한 번 생성하고 종료할 때 해제합니다.

Layout 이벤트 도중 컨트롤 수를 바꾸는 문제를 피하려고 GUILayout 대신 GUI 좌표를 쓰고, 버튼 동작은 다음 Update에 처리합니다. 프레임당 대기 동작은 최대 32개입니다. 스타일은 한번 만들고 한글 OS 글꼴을 요청하며 GUI 행렬·스킨·깊이·색상은 그리기 뒤 복원합니다. 모달 뒤 인벤토리는 투명한 Canvas로 마우스 클릭을 가립니다. 실제 입력과 글꼴 표현은 인게임 검증 대상입니다.

## 판정과 기록

`EnhanceService`는 `[Injectable(InjectionType.Singleton)]`으로 서버 전역에 한 번 등록합니다. SPT 4.1.6의 `[Injectable]` 기본값은 Transient입니다. 기본값을 쓰면 조회·아이템 이벤트 라우터가 서로 다른 서비스의 `pending` 사전을 보게 되어 방금 받은 견적도 실행할 때 사라집니다. 0.2.0 사용자 제보를 실제 `DependencyInjectionHandler`와 별도 라우터 해석으로 재현한 뒤 공유 수명으로 수정했습니다. 프로필별 견적과 중복 차감 방지 잠금이 한 인스턴스에 유지됩니다.

1. 프로필 로드의 `EftClientBackendSession.GetProfiles`가 완료되면 `/rf/gear-enhance/state`에서 소유 장비의 강화 기록을 읽습니다. 원래 로드 Task는 유지하고 읽기 전용 동기화를 이어 기다립니다. 실패해도 게임 로드 자체를 실패시키지 않으며 새 프로필에는 옛 기록을 적용하지 않습니다.
2. 창을 열면 인벤토리 큐와 효과 기록을 먼저 동기화하고 `/rf/gear-enhance/quote`로 아이템 ID·항목·F12 설정을 보냅니다. 최초 기록 동기화가 실패하면 결제 견적을 진행하지 않습니다.
3. 서버는 소유·창고 위치·분류·내구도·잠금·빈 보관칸·항목 종류·설정 범위를 확인하고 본체 기준가와 단계로 비용을 산출합니다. 무기에 방어구 항목을 고르거나 그 반대는 거절합니다.
4. 60초 견적을 프로필마다 하나 보관합니다. 새 견적은 이전 것을 대체하며, 장비·부품 상태의 지문과 선택 항목·현재 단계를 저장합니다.
5. 실행은 SPT의 `SendOperationRightNow`로 보내는 커스텀 `GearEnhance` 아이템 이벤트입니다. 서버가 견적·상태·항목·루블·파괴 확인을 다시 검사한 뒤 난수를 뽑습니다. 검증 전에 차감하지 않습니다.
6. SPT `InventoryHelper`로 루블 묶음을 차감하고 파괴 시 아이템 트리와 보험을 제거합니다. 내구도 0은 원래 아이템 변경 응답으로 돌려줍니다. 일반 인벤토리 동기화 경로를 사용합니다.
7. 성공 시 `rfGearEnhance.Tracks[itemId][path]`의 선택 항목 단계만 올립니다. 다른 항목은 보존하며 모두 함께 적용합니다. 일반 실패는 설정에 따르며, 하락은 선택 항목만 1단계 내립니다. 파괴는 본체·부품의 Tracks와 레거시 메타데이터를 모두 삭제합니다.
8. 클라이언트는 서버 영수증을 확인한 직후 효과 캐시를 갱신하고, 전체 소유 기록과 다시 맞춥니다. 실행 결과가 미확정이면 자동 재시도하지 않습니다.

항목별 단계로 비용과 최대 단계를 판단합니다. 항목 선택 자체는 비용·확률을 소모하지 않습니다. 0.2.x `Levels/Paths`는 같은 항목의 `Tracks`로 한 번 옮겨 무료 복제나 단계 손실을 막습니다. 0.1의 단계만 남은 장비는 첫 항목에 기존 단계를 무료·100%로 복원합니다. 조회 API에는 통신 버전5를 요구합니다. 이전 버전에는 보호/진화 계약과 진화 기록이 없어 조회 전에 거절합니다.

## 단계 곡선·완성과 고위험

EnhanceProgression은 클라/서버 공통 순수 계산입니다. 최대 단계 M, 절반 H=ceil(M/2), 단계 L에서 증가 가중치는 H까지 1, 그 뒤 선형으로 4까지 증가합니다. 누계는 `L + 3k(k+1)/(2(M-H))`, k=max(0,L-H)이며 최대 1~2단계도 별도 유한 분기로 처리합니다. 효과는 `min(기본 증가량×M, 효과 상한) × 현재 누계 / 최대 누계`입니다. 초반 증가량은 같고 후반 증가폭만 커지며 최종 기본 효과는 유지합니다. 기존 중간 단계 효과도 새 곡선으로 다시 계산합니다.

무기3종/방어구2종이 모두 M 이상이면 IsComplete는 진화 자격만 나타냅니다. 자동 보너스는 없으며 별도 Evolve 작업 성공 후 EvolvedItems에 itemId를 기록합니다. snapshot의 각 EnhanceRecord.Evolved와 영수증의 IsEvolution/Evolved를 동기화합니다. Amount는 이 진화 기록에만 보너스를 곱하고 Badge/배경도 IsEvolved로 판단합니다. 일반 최대 단계 기록을 무료 진화로 이전하지 않습니다. 원본 템플릿·수리 Buff에는 쓰지 않습니다. 진화 후 기본+20%, 최종 안전 상한은 감소율80%/인체공학추가50이며 프레임당 전체 인벤토리 탐색은 없습니다.

성공률은 `max(0, 시작 성공률 - 선택 항목 현재 단계 × 감소량)`이며 항상 성공/레거시 무료 복원은 100%입니다. 무기 3종이 모두 H 이상이고 고위험 기능이 켜지면 일반 실패 설정 대신 별도 판정(실패 중 기본25% 파괴, 나머지는 선택 항목 -1)을 사용합니다. 방어구는 일반 실패 설정을 따릅니다. 견적의 DestructionPercent는 실패 조건부 확률이고 CanDestroy는 확인란 기준입니다. 성공률100이면 확인이 필요 없습니다. 실제 파괴/하락 결과만 영수증에 기록하고 캐시는 다시 추첨하지 않습니다. 지문에는 전체 항목 단계도 포함해 다른 항목이 바뀌면 결제 전 거절합니다.

## 보호 체크 칸과 비용 계약

EnhanceProtection은 견적 요청에만 들어가는 파괴/하락 bool 두 개이며 F12 영구 옵션이 아닙니다. 서버가 원래 실패 결과와 현재 단계·실패 가능성으로 각각 유효한지 판단합니다. +0 하락·100% 성공·확률0인 손실에는 보호를 적용하거나 과금하지 않습니다. 두 보호비는 `ceil(기본 비용 × 시도 단계² × 각각의 계수/100)`입니다. 기본50/35, F12 범위0~1000입니다. 선택하지 않은 예상 보호비는 long으로 보관하므로 그 비용만1억을 넘는다고 기본 견적까지 거절하지 않습니다. 실제 선택된 총액만1억 이하를 요구합니다.

보호를 바꾸면 새 견적을 발급하고 이전 QuoteId는 무효화합니다. 이벤트는 서버에 저장한 옵션·가격만 사용합니다. 기존 성공 판정과 실패 중 파괴 추첨을 한 번 수행한 뒤 선택 보호에 해당하는 원래 손실만 KeepItem으로 바꿉니다. 다른 손실로 전환하거나 재추첨하지 않습니다. DestructionPrevented/DowngradePrevented는 영수증·프로필에 저장하고 UI에서 보호 발동을 설명합니다. 비용은 결과와 관계없이 총액을 한 번 차감하며 기존 아이템/루블 네이티브 경로를 유지합니다. 파괴 보호가 유효하면 CanDestroy가 false여서 추가 파괴 확인란은 생략할 수 있습니다.

결과 확인창은 서버 영수증 이후에만 열고 결과·현재 단계·비용·보호 발동을 크게 표시합니다. 성공/완성은 녹색/보라색, 손실은 빨간색, 보호 발동은 금색입니다. 확인 전에는 뒤쪽 버튼·보호·항목·드래그를 비활성화하며 거래 함수에도 resultVisible 검사를 둡니다. 결과 문구는 순수 ResultText로 분리해 실제 파괴·하락과 보호된 실패가 혼동되지 않는지 검사합니다. 창 자체는 기존 캐시된 스타일·텍스처를 사용하고 네이티브 아이템 뷰에는 새 후처리를 넣지 않습니다.

## 별도 스타 강화 진화와 개발자 옵션

일반 창에서 IsComplete && !IsEvolved인 경우에만 진화 창 버튼을 엽니다. 진화는 별도 GUI.Window ID/캐시된 콜백과 760×870 레이아웃을 사용하며 일반 보호 창(760×950)과 구분합니다. 서버도 모든 현재 최대 단계·소유/창고·미진화 조건을 다시 확인합니다. QuoteRequest.Action=Evolve가 유효한 경우 최대 단계 Cost 거절을 우회하는 대신 별도 진화 가격/성공률을 계산합니다. 기본50%, 본체 가격300%, 항상 성공 개발자 옵션은100%입니다. 보호 유효성은 진화에서 항상false, 실패모드는Destroy이며 확인란·본체 트리/보험 제거를 유지합니다.

성공은 단계 증가 없이 EvolvedItems만 추가합니다. 실패는 트리 삭제와 진화 기록 삭제를 함께 합니다. pending 지문에는 진화 여부도 넣어 실행 전 변조를 감지하고 이미 진화한 장비의 재진화를 거절합니다. 일반 강화 후 항목 추가/하락은 영수증 Evolved를 보존하며 보너스는 중복 저장하지 않습니다. 기존 프로필에 진화 필드가 없으면 빈 집합으로 시작합니다.

확률·비용·성공 보장·실패·능력치·보호·진화 설정은 BindDeveloper가 ConfigurationManagerAttributes(Browsable=false, Category=99.개발자옵션)를 붙입니다. 기존 cfg 키/값은 유지합니다. 일반 메뉴/효과음 설정은 일반 Bind입니다. 개발자 표시 토글은 metadata만 바꾸고 견적을 무효화하지 않습니다. ConfigurationManager는 다시 열 때 목록을 갱신하므로 토글 설명에도 F12 재열기를 안내합니다. 실제 해당 플러그인의 Unity 렌더링은 별도 검증 대상입니다.

## 음원에 맞춘 진행과 결과 연출

AttemptTimeline은 현재 재생 시계와 실제 음원 길이를 받아 Update에서 완료를 한 번만 소비합니다. 사용자 강화중소리.mp3의 PCM 프레임211766/48000Hz = 4.4117916667초입니다. 전용 AudioSource.PlayScheduled에 오디오 DSP 시각+0.05초를 예약하고, 게이지도 같은 시작 시각과 AudioSettings.dspTime을 씁니다. 따라서 프레임 수나 MP3 컨테이너 패딩 길이에 의존하지 않습니다. 소리가 꺼지거나 기본음/연결 실패 대체일 때는 Stopwatch 단조 시계를 사용하되 음원에서 읽은 시간은 유지합니다.

첫 클릭으로 견적·확인 여부·세대 번호를 고정하고 완료 전 전송·중복 시작을 차단합니다. 종료 경계는 started+duration과 비교해 부동소수점 나눗셈 때문에 100%를 놓치지 않게 합니다. 서버 호출 전 인벤토리 큐·설정·창고 상태를 다시 검사합니다. 효과음 설정 변경만으로는 견적을 무효화하지 않습니다. Sleep·대기 루프·프레임마다 Task 생성은 없고, 서버 응답 지연은 가득 찬 게이지로 기다립니다. 결과 미확정 자동 재시도는 금지합니다. 이는 클라이언트 연출 시간이며 서버의 별도 타이머 제약은 아닙니다.

영수증 후 미리보기에 1.2초 색상 플래시와 파괴 조각을 그립니다. 조각은 기존 Sprite를 3×3으로 나누어 9회 이하 그리며 좌표·UV를 직접 잘라 창 안으로 제한합니다. GUI 행렬 회전·Repaint 전용 GUI 그룹·새 텍스처·파티클은 사용하지 않습니다. 표시용 스프라이트 확보 오류는 영수증 처리와 분리하고 종료 시 보관 참조를 해제합니다.

| 조작성 | `Weapon.get_ErgonomicsTotal` | 선택 무기에 고정 인체공학 추가, 최종 무기 값 0~100 |
| 정밀성 | `Weapon.GetTotalCenterOfImpact`, `get_TotalShotgunDispersion` | 총알의 기본 탄 퍼짐과 산탄 패턴 퍼짐 각각 감소 |
| 내구성 | `ArmorComponent.ApplyDurabilityDamage` 앞 | 실제 차감 인자를 감소. 총격·폭발 양쪽에서 호출됨 |
| 기동성 | `ArmorComponent`의 세 페널티 getter 뒤 | 해당 장비의 음수 이동·회전·인체공학 페널티를 완화 |

실제 게임 DLL에서 `ShotEffector.RecoilDelta`, `FirearmController.TotalErgonomicsFunc/WeaponModified`, `Player.RecalculateEquipmentParams`와 피해 처리 함수들이 이 지점을 읽는 것을 검사합니다. 존재하는 이름만 확인하고 끝내지 않고 호출 경로도 대조합니다.

부착물 반동 -40%인 총에서 +10 반동 제어 15%라면 `0.6 × 0.85 = 0.51`, 즉 새 delta는 -49%입니다. 단순히 delta에서 15를 빼는 식으로 계산하지 않습니다. 전역 반동 보너스와 별도 카메라 반동은 이 효과의 대상이 아닙니다.

방어구 부품은 현재 장착 부모를 최대 64번 따라가 요청한 항목의 기록이 있는 가장 가까운 강화 장비를 확인합니다. 다른 항목만 기록된 부품에서는 해당 항목을 부모에서 계속 찾습니다. 본체와 부품 효과를 중첩하지 않습니다. 루트가 자기 자신을 가리키거나 두 부모가 순환해도 종료합니다. 일반 getter에서는 HTTP나 원본 템플릿 쓰기를 하지 않습니다.

페널티의 기본 아이템 검사 카드에는 `EquipmentPenaltyComponent.Template`을 직접 읽는 코드도 있습니다. 이 범위에만 소유 컴포넌트를 함께 전달하는 명령 변환을 적용하여 본체 페널티 표시도 장비별로 줄입니다. 기존 부품 합산은 유지하며 원본 Template은 그대로 둡니다. 변환은 컴포넌트의 정확한 Template 필드 바로 뒤에 있는 세 getter만 대상으로 합니다.

## F12와 캐시

효과별 증가량·상한은 F12에 각각 노출하며 레벨 상한과 분리합니다. 서버와 클라이언트가 `EnhanceEffects`의 동일한 식으로 견적을 표시하고 효과를 계산합니다. 기존 장비도 새 F12 증가량·상한을 사용합니다.

프로필 기록은 `itemId → 항목 → 기록`의 사전을 복사하여 교체하는 캐시에 보관하고 설정도 새 객체로 교체합니다. GameBridge의 반복 멤버 조회는 캐시하며 기본 읽기는 표준 reflection을 사용합니다. 게임용 Harmony의 Mono 도구를 .NET 테스트 실행기에서 초기화할 필요가 없도록 분리했습니다.

정적 `EFT.InGameStatus.InRaid`도 이 캐시로 필드·속성을 구분해 읽습니다. 실제로는 필드인 멤버를 매번 Harmony 속성 조회로 시도하던 경고 반복을 제거하며, 캐시에 저장하는 것은 멤버 정보이고 레이드 상태 값은 매번 다시 읽습니다.

설정 변경과 동기화 후 선택 아이템 속성, 실제 플레이어의 장비 페널티, 손에 든 무기의 캐시·반동 계산을 메인 스레드에서 갱신합니다. 늦게 도착한 이전 동기화는 새 프로필 기록을 덮거나 비우지 않도록 세대 번호로 걸러냅니다. 플러그인 종료 시에도 미완료 요청을 무효화합니다.

## 표식·소리·창 성능

`ItemMarkers`는 실제 `GridItemView.UpdateInfo` 후처리와 `GetItemName(ItemAddress)` 후처리에 연결합니다. 강화 기록이 있는 확인된 아이템에 네이티브 수리 특성과 같은 배경색 `(209,153,45,32)/255`를 적용하고 이름에 금색 `★ +총 단계`를 붙입니다. 별도 진화 성공만 `(163,103,232,65)/255` 보라 배경과 `#B989F5` ★★ 진화 이름 표식으로 구분합니다. 0.3.1의 getter 없는 선언 건너뛰기·표식 예외 차단은 유지합니다. 장전·충돌·원래 오류색은 보존합니다. `BuffComponent`, `Upd.Buff`, 템플릿은 수정하지 않습니다. 활성 뷰는 최대 2048개만 기록하고 `ItemView.Kill`에서 제거합니다. 영수증/동기화 후 선택 아이템의 뷰만 갱신하며 매 프레임 전체 인벤토리를 순회하지 않습니다.

사용자 원본 음원6개는 src/Client/Audio의 PCM16 WAV를 EmbeddedResource로 DLL 안에 넣습니다. 원본 MP3는 assets/audio/source에 보존하고 SHA256·프레임 수·변환은 provenance.json에 기록합니다. 일반/결과5개는 FFmpeg로 오디오 트랙만 디코딩했고, 심장박동은 사용자 요청으로 마지막4.411791667초(시작27.305124433초)를 잘라 charge×0.8 + heartbeat×0.45로 혼합했습니다. 심장박동에만 시작40ms/끝70ms 페이드를 적용했고 두 충전음의 프레임 수는 동일합니다.  빌드/실행 시 FFmpeg나 MP3 코덱은 필요 없습니다. 코드 MIT와 별도인 사용자 제공 자료입니다.

WaveSound는 파일 크기16MiB·블록 경계·PCM16/1~2채널/8~96kHz·60초 이하를 확인하는 순수 파서입니다. 루프는 파일 끝으로 반드시 전진하고 샘플 수로 제한합니다. 시작 시 AudioClip6개를 한 번 만들고 일반 성공/진화 성공은 각각 success/star2 파일을 쓰고 실패/하락은 failure 파일을 공유합니다. 일반/진화 충전음은 charge/evolution_charge로 분리합니다. 전체 관리 프레임 파싱·클립 생성은 창 열기나 OnGUI에서 하지 않습니다.

EnhancementAudio는 자체 AudioSource의 spatialBlend0/loopfalse로 재생하며 GUISounds.GetCommonSoundsMixerGroup의 실제 UI 믹서를 연결합니다. 마스터/인터페이스 볼륨을 우회하지 않습니다. 전용 음량은 기본70%, UI 믹서 연결 실패 시 기본음으로 대체합니다. 새 소리 시작 전 자체 이전 소리만 멈추며 네이티브 오디오 소스에는 쓰지 않습니다. 창 종료 시 자체 재생 중단, 플러그인 종료 시 소스·클립6개 해제입니다.

기본음 대체는 Singleton<GUISounds>.PlayUISound를 사용합니다. 시도 MenuInstallModFunc, 성공 RepairComplete, 일반 실패/하락 ErrorMessage, 파괴 MenuWeaponDisassemble, 진화 성공 QuestCompleted입니다. 결과음은 유효한 서버 영수증 후에만 큐에서 재생하고, 재생 예외는 비용/영수증/재전송과 분리합니다.

`Update`의 창고 상태 확인이 매 프레임 호출하던 `AccessTools.TypeByName`은 Harmony 내부에서 `AllTypes/Assembly.GetTypes`를 다시 검색합니다. 게임 타입은 `GameBridge.RuntimeType`에 캐시하여 이 반복 작업을 제거했습니다. 메뉴·조회·실제 능력치 경로도 같은 캐시를 사용합니다. 캐시 적중 1만 회의 추가 관리 할당 0을 테스트합니다. 이 수치는 Unity의 실제 창 FPS를 의미하지 않습니다.

창을 닫을 때 Repaint CPU 평균/최대 시간을 한 번 기록합니다. GPU 시간·프레임 전체 비용은 포함하지 않으며, 실제 성능 개선률과 다른 모드 조합은 동일 장면에서 비교해야 합니다. UI 좌표 회전·반복 스타일 생성·반복 타입 스캔은 이번 수정에서 제거했지만 실제 플레이에서 개선을 확인한 것은 아닙니다.

## 검증 범위

- 서버·공통 검사: 비용·재요청·실패·저장·범주·항목별 독립 강화·기존 기록 이전·효과 식·상한·프로필 분리. 실제 SPT 등록기에서 따로 해석한 라우터 사이의 견적·결제·영수증 공유도 검사합니다.
- 클라이언트 검사: 실제 컴파일한 postfix/prefix를 모의 아이템에 실행하여 다섯 효과와 아이템 분리를 검사합니다. 실제 페널티 변환 결과로 DynamicMethod를 만들고 실행하며, 템플릿이 그대로인지 확인합니다. 타입이 있는 콜백 연결, 동시 3종 적용·항목별 부모 상속, 아이콘 마스크와 소리 선택도 실행합니다.
- 게임 API 검사: 실제 게임 DLL을 Mono.Cecil로 읽어 시그니처와 호출 경로를 대조합니다.
- 별도 게임 설치·서버 실행·게임 코드 실행·가짜 게임 참조 DLL은 검사에 필요하지 않습니다. 테스트용 작은 아이템 객체는 테스트 프로젝트에만 있고 게임 플러그인에는 포함하지 않습니다.

이는 실제 Unity의 Harmony 패치 설치, 게임 화면, 반동 체감·피격 결과, 다른 모드와의 조합을 검증한 것은 아닙니다. 컴파일 참조 모듈도 실제 사용자 게임 모듈과 구분하며, 배포 패키지는 실제 게임 설치 경로에서 다시 빌드해야 합니다.

## Visual Studio 패키징

`GearEnhance.sln`은 클라이언트·서버·검사 프로젝트와 `GearEnhance.Package.csproj`를 포함합니다. 패키징 프로젝트는 두 런타임 프로젝트를 `ReferenceOutputAssembly=false`로 참조하여 빌드 순서만 연결하고 게임에 설치할 DLL에는 참조되지 않습니다.

Release 빌드 후 `tools/Packaging.targets`가 실제 게임 설치 경로를 확인하고 현재 구성의 두 `GetTargetPath` 결과만 수집합니다. 중간 스테이징 폴더를 매번 비워 제거된 파일이 섞이지 않게 하며, MSBuild `ZipDirectory`로 임시 ZIP을 완성한 뒤 `Build/GearEnhance-$(Version).zip`으로 이동합니다. 게임·SDK·NuGet 의존 DLL은 넣지 않습니다. Visual Studio의 빠른 최신 상태 판정을 패키징 프로젝트에만 끄므로 변경이 없는 재빌드에서도 ZIP을 갱신합니다.

Debug·디자인 타임 빌드에는 압축하지 않습니다. 컴파일 전용 환경의 `GearCreatePackage=false`는 압축을 생략합니다. Python 스크립트는 이 옵션으로 먼저 빌드·검사를 마친 뒤 같은 패키징 타깃을 실행하므로 두 방식의 설치 경로 구성이 같습니다. Visual Studio의 일반 빌드는 검사 실행을 포함하지 않습니다.

## 남은 범위

SPT 일반 프로필 저장 주기를 사용하며 강제 종료용 별도 복구 저널은 없습니다. 아이템 ID가 바뀌는 판매·분해·재조합에 기록을 옮기지 않습니다. 다른 세션의 인벤토리 변경과 공유하는 외부 잠금도 없으므로 이 모드는 싱글플레이어 범위입니다. 같은 계산 지점을 바꾸는 모드와의 중첩은 실제 설치 조합에서 확인해야 합니다.
